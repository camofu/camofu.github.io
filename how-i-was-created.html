How I was created

I'm a small language model running on Carlo's laptop. Here's the whole stack — the model, the retrieval pipeline, the path your message travels, and the sandbox that keeps me from doing any damage.

The two halves

This site is split deliberately into two pieces that live in completely different places:

  • A public website — the page you're reading now. It's just static files (HTML, CSS, an image, a little JavaScript) served for free by GitHub Pages. No code runs on GitHub's side; the files are handed to your browser as-is.
  • A private chatbot server — a Python program running on Carlo's laptop. It wraps a local language model and exposes exactly one useful HTTP endpoint, POST /chat.

The website is the front door; the chatbot is the brain. They live in separate repositories on purpose — if the model code and the prompt-engineering files were in the website repo, GitHub would happily serve them as plain-text downloads to anyone curious enough. Keeping them apart means the only thing the public can reach is one narrow API.

Nothing about me runs in the cloud. There's no OpenAI key, no hosted inference. The model weights and every generated token come off a single GPU in a laptop.

The model and the retrieval pipeline

The brain is Mistral-7B-Instruct, a 7-billion-parameter open-source model, loaded in 4-bit quantisation via transformers and bitsandbytes. Quantising the weights down to 4 bits is what lets the model fit in roughly 5 GB of GPU memory instead of the ~14 GB the full-precision version would need.

On its own, a 7B model doesn't know anything specific about Carlo. That's where RAG (Retrieval-Augmented Generation) comes in:

  • A small embedding model — sentence-transformers/all-MiniLM-L6-v2, running on the CPU — turns text into vectors.
  • Carlo's CV is kept as a set of markdown notes (bio.md, skills.md, education.md, and a big persona.md).
  • When you send a message, the retriever finds the few notes most relevant to your question and stitches them into the system prompt — the instruction text the model reads before it ever sees your message.

persona.md is the important one: it's a decision tree telling the model how to behave as "Carlo" — how to greet, how to answer technical questions, when to admit it doesn't know, what to refuse. RAG is what lets a small, generic model speak with specific facts without ever being re-trained.

The path your message travels

Everything is glued together by a Python server (server.py) built on FastAPI and Uvicorn, with Pydantic validating incoming JSON and slowapi enforcing rate limits. When you hit "Send", here's the round trip:

  1. The page's JavaScript packages your message plus the recent conversation history into a JSON POST request.
  2. That request crosses the public internet to a Tailscale Funnel tunnel, which terminates TLS and forwards it to the laptop. The server itself only listens on 127.0.0.1:8000 — the loopback interface — so the tunnel is the only way in.
  3. The server validates the input, checks the rate limit and daily cap, retrieves relevant context, and builds the system prompt.
  4. Mistral generates a reply on the GPU.
  5. FastAPI returns JSON — {"reply": "…"} — back through the tunnel, and the JavaScript drops the text into the chat window.

A second endpoint, GET /health, just returns {"ok": true} so the tunnel and any monitoring can check whether I'm awake.

Stateless by design

The server keeps no per-user memory. Every request from your browser carries the entire (trimmed) conversation along with the new message; the server forgets everything the moment it answers. The whole conversation lives only in your browser tab.

This is a deliberate privacy and simplicity choice: there are no sessions to track, no caches to expire, and — if the server were ever compromised — nothing useful for an attacker to steal, because there's no conversation history sitting on disk.

The security model

The model itself is harmless — Mistral can't read a filesystem. The risk is the surrounding software: FastAPI, Uvicorn, PyTorch and a couple hundred transitive dependencies all become internet-reachable the moment the tunnel is on. One remote-code-execution bug in any of them, and an attacker would be running code on a daily-driver laptop. So defence happens at two layers.

Layer one — guards inside the server

These don't stop a machine compromise; they stop cost runaway and obvious abuse.

GuardWhat it prevents
CORS allowlist — only camofu.github.ioOther sites embedding the bot in their pages
Per-IP rate limit — 10 requests/minOne client hammering the endpoint
Daily cap — 500 requests/dayBurning a whole day's compute budget in one afternoon
Input length cap — 800 charactersMegabyte-long prompts sent to OOM the GPU
Server-side history trim — last 6 turnsClients inflating context by lying about history length
Generation lockTwo requests colliding on the single GPU at once
Bound to 127.0.0.1Any direct internet access that bypasses the tunnel

Layer two — an OS-level sandbox

The server runs as a dedicated, locked-down system user (chatbot) with no login shell, no home directory, and ownership of nothing except one scratch folder. It's launched and supervised by systemd, which applies a long list of kernel-enforced restrictions before any Python runs:

  • The entire filesystem is mounted read-only except one writable workspace (/var/lib/chatbot) and a private /tmp.
  • Read access to the project code is granted narrowly via ACLs — the chatbot user can traverse to exactly the project directory and nothing else under /home.
  • ~/.ssh and ~/.gnupg are explicitly blanked out, on top of being unreadable already.
  • No new privileges, zero Linux capabilities, no setuid escalation, no realtime scheduling, no new namespaces.
  • Can't load kernel modules, change sysctls, read kernel logs, touch the clock or hostname, or see other processes.
  • Only AF_INET, AF_INET6, and AF_UNIX sockets — no raw or packet sockets.

The upshot: even a complete RCE-class compromise of the Python process lands the attacker in a read-only box with no credentials, no other processes, and no useful loot.

What's left as residual risk

Two things this design doesn't fully eliminate. Prompt injection — clever messages trying to make me say something off-script — is partly handled by the persona decision tree and partly an irreducible fact of any public LLM. And a kernel exploit could in principle escape the sandbox; the airtight fix (a VM with GPU passthrough) wasn't viable because the laptop's single GPU shares an IOMMU group with the boot SSD, so it can't be isolated to a VM without faking guarantees the hardware doesn't make. Running on a dedicated GPU VPS is the available "zero-risk" upgrade if it's ever worth it.
